# Agent Note: 随发布说明交付经过验证的桌面源码

Status: implemented

[English](2026-10-26-desktop-release-sources.md) | 中文

## 问题

桌面版本包含经过修改的 Cut 程序，但源码固定标识和补丁不能独自交付完整源文件。编译器符号用于调试，而且私有保存时间有限。自动生成的提交说明无法向用户说明安装范围和已知限制。

## 决策

[桌面发布工作流](../../../../.github/workflows/desktop-release.yml) 从与原生构建相同的工作树和源码清单组装完整 Harness、上游 Cut、补丁后 Cut 和 Whisper Git 归档。[归档器](../../../../scripts/desktop-release-sources.py) 拒绝受跟踪的工作树修改，验证固定 commit 和 tree，应用每份经过摘要检查的补丁，并将 tar 文件字节和权限与生成的 Git 对象对照。固定 tar 和 gzip 时间戳使相同输入产生相同源码归档。归档只包含受跟踪的源文件，不包含未受跟踪的构建输出和 profile。

源码归档、commit/分发清单和构建说明共用安装包的校验清单与公开发布路径。源码验证失败会在发布前阻止组装。[调试符号](2026-10-22-desktop-package-size.zh.md) 继续遵守独立的访问和到期规则。源码资产不授予第三方再分发权，也不替代精确分发审查；[TOS 发布](2026-10-16-tos-desktop-distribution.zh.md) 保留审批、不可变对象和通道检查。

正式发布要求通过 `release_notes` 输入提供明确的用户说明。验证会在签名工作开始前拒绝空白说明，不发布的构建仍可不带说明运行。创建 release 的步骤通过环境变量将输入文本写入临时文件；说明中的 shell 语法保持为数据。

## 考虑过的替代方案

**只发布源码固定标识和补丁。** 接收者仍需自行还原缺失的源文件。因此发布会交付所选 Git tree 的完整内容，并记录其身份。

**复用本地候选的源码归档。** 这些文件可能对应其他 commit 或补丁集合。组装会为本次发布工作树重新还原源码。

**使用自动生成的提交说明。** 提交主题不能可靠说明支持的平台、升级步骤或用户可见限制。因此正式发布要求事先准备用户说明。

## 影响

组装需要下载固定源码 commit，并为发布增加源码交付体积。源码验证会拒绝不支持的子模块、归档属性造成的遗漏和越界链接，而不是宣称完整交付。隔离的 Git fixture 验证归档内容和可复现性、错误固定标识拒绝、脏源码拒绝与已有输出保护；工作流测试验证说明准入和字面传递。原生签名、公证、最终 GUI 行为及实质分发资格仍需独立的发布证据。
