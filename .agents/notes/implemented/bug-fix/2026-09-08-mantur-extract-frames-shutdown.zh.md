# Agent Note: 关闭编辑器前等待本地抽帧完成

Status: implemented

[English](2026-09-08-mantur-extract-frames-shutdown.md) | 中文

## 问题

[编辑器退出实例](2026-09-08-mantur-editing-owned-shutdown.zh.md)将本地抽帧判为未确认。该路由已经返回原始异步工作，但拼图清理吞掉失败，Python 标注没有经过媒体进程管理。场景分析和单帧失败可能返回部分预览，却没有为退出保留失败操作。

## 决策

第三层编辑器补丁把 `openchatcut-extract-frames` 接入既有请求管理。已接受的请求保留原始完成结果，包括浏览器停止输入后继续提交的工作。截止后拒绝新请求。FFmpeg 和 FFprobe 继续保留既有的具体子进程句柄；Python 标注使用同一进程管理。操作错误和既有超时期限只在子进程发出 `close` 后才结束等待，包括继承的输出管道。退出不会取消已接受的抽帧。

抽帧和拼图临时目录删除均继续等待并传播错误。即使上游预览行为返回部分内容，场景分析、单帧抽取和标注失败仍保留在请求失败记录中。不增加回退，不清除既有失败。共享拼图代码还服务于 render-still；其渲染器退出限制保持不变。

## 考虑过的替代方案

**只允许插件名，不检查被调函数。** 这样会把 HTTP 响应无法证明完成的清理和子进程工作误判为通过。

**去掉失败采样并忘掉错误。** 预览可以有用，同时操作仍有失败工作；退出结果必须保留这一差别。

## 影响

真实 HTTP 回归新建半秒本地 H.264 视频，覆盖指定时间点和自动场景采样，写入返回的 JPEG，用 FFmpeg 完整解码，并确认源字节不变。受控请求体跨过准入截止；已接受请求继续完成，新请求被拒绝。夹具子进程退出后，其后代继续持有 stderr，证明抽帧仍等待实际 close。HTTP200 返回后，延迟清理仍保持未完成。清理、部分帧、场景分析和拼图清理失败均拒绝缓存的退出结果。移除清理错误传播或部分帧失败记录时，对应负向控制会失败。

浏览器冻结和保存确认采用受控 broker 夹具。这证明后端请求、媒体和文件生命周期，不代表完整 AgentLoop 附件或已安装客户端流程。本地上传、Remotion、远程生成及其他未接入的工作来源需要独立证据。依赖、锁文件、音频收尾及用户剧集工程均未修改。
