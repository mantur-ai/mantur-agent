# Agent Note: 桌面账号升级时显式重新授权

Status: implemented

[English](2026-09-09-native-account-reauthorization.md) | 中文

## Problem

已安装桌面应用替换为 browser-account-v2 代码后，仍可能保留版本 1 账号数据库。若在 Host 初始化时直接拒绝该数据库，用户就无法进入浏览器登录或跳过登录。

## Decision

Main 在启动 Host 前检测版本 1。原生本地化对话框默认选择退出。只有用户明确确认后，才会在账号目录旁创建私有、经过所有权检查的备份，并将账号数据库替换为空的版本 2 存储。备份保留操作系统加密的原始字节；此操作不会解密、导入或远端撤销旧凭据。项目、草稿、模型凭据及其他账号文件均不在操作范围内。

替换数据库与备份文件在原子发布前完成同步。发布失败保留原数据库；目录同步失败会尝试恢复预先准备的原始副本。如果恢复本身失败，不可变备份仍被保留，启动停止并显示固定、不含秘密的恢复提示。未知版本、不安全目录及未完成的 SQLite 操作都会阻止替换。操作期间，Main 持有应用单实例锁，尚未启动账号所有者。

Windows 恢复会明确失败，因为 Node 不提供所需的持久化目录发布能力。该平台仍可使用新的版本 2 profile。[桌面 README](../../../../apps/desktop/README.zh.md) 说明面向用户的行为。

## Alternatives considered

**静默丢弃或导入旧账号记录。** 这两种方式都会在未经明确同意时改变凭据权限；导入还暗示 native-account-v1 与 browser-account-v2 之间存在并未支持的兼容性。

**启动时拒绝所有旧 profile。** 这种做法保留了数据，却阻止普通已安装用户通过升级进入账号引导流程。

## Consequences

确认升级后，需要重新在浏览器授权或明确选择跳过。私有备份是恢复资料，不是有效登录；本地替换也不表示旧服务端授权已撤销。合成数据库与 Main 对话框测试覆盖取消、私有备份、替换失败和恢复；实际安装包的浏览器返回与操作系统存储仍需在每个交付平台及架构上单独验收。
